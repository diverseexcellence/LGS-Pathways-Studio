2. Executive Summary
2.1 Project Background
Liberty Grove Schools (LGS) currently relies on a fragmented combination of source systems (PowerSchool for demographics; ILEARN, IXL, Acadience, IREAD, and WIDA for assessments) to make data-informed decisions about student support tiers. There is no single, secure, role-aware platform where LGS administrators can ingest these data sets, automatically calculate a recommended support tier for each student, finalize the recommendation, and track a complete audit history of every decision.
Over the past several months, Diverse excellence Technology (DET) team has built a working prototype, referred to in this document as “LGS Pathways Studio”, that demonstrates the desired end-to-end workflow. The prototype demo reviewed on April 9, 2026, to LGS stakeholders, produced a substantial set of clarifications, change requests, and functional requirements that this document captures formally so the application can move from prototype to production-grade build.
As the project moves toward MVP readiness, this document will serve as the agreed requirements baseline for development, QA validation, stakeholder review, and first-release approval. The prototype remains a useful reference for reviewing the workflow and user experience, while the approved requirements will guide what is built for the MVP. 
2.2 Business Objectives
Centralize and standardize the ingestion of student demographic and assessment data from multiple source systems into a single secure repository.
Automate the calculation of a recommended tier (Tier 1, Tier 2, Tier 3) for every student with sufficient data, eliminating manual cross-referencing across spreadsheets.
Provide an administrator-controlled review/finalize workflow so that a human owns every tier decision and an immutable audit trail is preserved.
Surface AI-generated, narrative academic progress summaries to support data-talk conversations.
Offer institutional-level dashboards and drill-down navigation (school → grade → homeroom teacher → student) so leaders can monitor distribution of students across tiers, growth trends, and intervention caseload at a glance.
For the MVP release, these objectives will be delivered with a focus on the core administrator workflow required. The application will help administrators review student information by showing proficiency levels, performance context, and approved mapped values rather than only raw scores or source-system data. Tier recommendations will follow the approved LGS rules, with the administrator responsible for reviewing and finalizing the decision. AI-generated summaries will support academic review discussions by providing clear student performance context, while final tier decisions will continue to follow the approved tiering logic and administrator review. 
2.3 Scope of This Document
This Business Requirement Document defines the functional and non-functional requirements for the MVP release of LGS Pathways Studio. The MVP is restricted to the Administrator user persona, with a planned future phase for a read-only Teacher view as confirmed in the April 9, 2026, meeting. Predictive analytics is explicitly out of scope; the AI feature is limited to summarization of existing data.
The scope of this document is centered on the core MVP administrator workflow, including approved data upload, student profile review, system-recommended tiering, administrator finalization, audit history, and the dashboard views required for MVP review. Dashboard metrics and drill-down views will be included where the related data, calculations, and first-release expectations are confirmed.
This document will help align LGS stakeholders, DET, development, and QA on what is expected for the MVP build.

3. Project Overview
3.1 Proposed Solution Overview
LGS Pathways Studio is a web-based application that consolidates the workflow into three primary modules, Data Ingestion, Students, and Dashboard accessed from a left-hand navigation. Authorized administrators upload categorized data files; the system normalizes records by Student Test Number (STN), generates a system-recommended tier with reasoning, and queues each student for human finalization. An AI assistant produces a narrative summary of each student’s academic progress. A real-time dashboard aggregates institutional metrics (tier distribution, average ELA growth, math proficiency, intervention caseload, target goal) and supports drill-down from grade level to homeroom teacher to individual student.
3.2 Goals & Success Criteria
3.3 In Scope (MVP)
Administrator authentication and Administrator-only access.
Data Ingestion module covering four configured data types: PowerSchool Demographics, ILEARN Checkpoint, IXL Diagnostic and Acadience Reading with the ability to add more data types post-MVP.
Student Directory with search and filter.
Student Profile screen with demographics, academic overview, raw assessment detail drill-in, AI-generated tier recommendation, finalize-tier workflow, AI-generated collaboration summary, and immutable audit trail.
Institutional Dashboard with KPI tiles, ELA/Math growth timeline, intervention caseload donut, grade-level proficiency summary, drill-down navigation to grade → homeroom teacher → student list, and a configurable Target Goal tile.
Export Report capability from the Dashboard.
3.4 Out of Scope (MVP - Future Phases)
Teacher user role and Teacher view (deferred to evaluate after MVP; teachers will not access the system at MVP per Velvet Wright).
Predictive analytics and machine-learning forecasting. The AI in MVP is summarization only.
Direct integration / API connections to source systems (PowerSchool, ILEARN, IXL, Acadience). MVP uses CSV upload only.
Learning Plans capabilities based on tier.
Parent / guardian portal.
Mobile-native applications. The MVP is a responsive web application.

5. Assumptions, Constraints, and Dependencies
5.1 Assumptions
Every student record across all data sources can be uniquely identified by Student Test Number (STN). The system uses STN as the canonical join key.
Source files are provided as CSV exports up to 10 MB per file. Larger files will be addressed in a future phase.
LGS will provide a definitive list of valid ethnicity codes from PowerSchool and the human-readable labels these should map to in the UI (e.g., the integer code “2” must be translated to its descriptive label).
LGS will provide or confirm mappings for other source-system values that need to be displayed in a readable format, including gender, enrollment status, lunch status, EL/ELL status, Special Education status, Section 504 status, and other approved demographic or program indicators.
LGS will confirm the authoritative tiering rules document (referenced in the meeting as “Sandip’s code rules”) before development of the production tier engine begins. The prototype currently encodes a draft rule set inferred from this document.
Grade level coding follows the convention where “0” means Kindergarten.
Each homeroom teacher is assigned to exactly one grade level (confirmed by Morrise Harbour).
5.2 Constraints
MVP must support only browser access. No native mobile build.
Target hosting platform is Microsoft Azure. The MVP and all subsequent phases will run on Azure App Service, Azure Cosmos DB, Azure Blob Storage, Azure Key Vault, and Azure Application Insights. 
AI summarization will use a Meta Llama-family large language model (model selection to be confirmed by the development team). The application architecture must keep the LLM behind an internal interface so the specific Llama variant or hosting can change without UI rework.
Development cannot be delayed further. Stakeholders agreed at the April 9 meeting that any new requirements not delivered shortly thereafter must be deferred to a later phase rather than blocking the MVP.


5.3 Dependencies
LGS must deliver a current, complete PowerSchool demographics export covering all enrolled students, including any that were missing from the initial sample (notably Grade 6 students).
LGS must deliver Acadience reading data files separated as Beginning of Year (BOY), Middle of Year (MOY), and End of Year (EOY) when available. The file naming convention should make the assessment window unambiguous.
LGS must provide ILEARN Checkpoint files separated by grade level and by checkpoint number (Checkpoint 1, 2, 3) and, where applicable, opportunity (Opportunity 1, 2).
DET must provide a list of STNs for which demographic information is missing so LGS can supply an updated demographics file.
LGS must confirm required source-system mappings for readable display values, including demographic, program, and assessment-related fields where applicable.
LGS/DET must provide or confirm the CSV export structure for each supported data type, including required columns, optional columns, accepted values, and any known source-system code mappings.

7. Functional Requirements - Data Ingestion Module
7.1 Module Purpose
The Data Ingestion module is the controlled entry point for all student data. It replaces the prior practice of dropping files into shared folders. The module must categorize each upload by data type, prevent duplicate uploads, surface a record count after each successful upload, and maintain a history of every file ever uploaded with the option to delete and re-upload incorrectly categorized files.
7.2 Screen: Data Ingestion
Header: “Data Ingestion” with subtitle “Securely upload student demographic and assessment data.”
Components:
Data Type dropdown (required). Pre-populated with the supported types listed below. Admin users can select from configured data types only.
File picker / drag-and-drop zone. Accepts a single CSV file at a time, up to 10 MB.
Upload Data button. Disabled until both a Data Type and a file have been selected.
Upload History table. Shows every file ever uploaded with Date, File Name, Data Type (implicit from the row's grouping or as a column), record count, and a Delete action.

7.4 Detailed Requirements
DI-1 Categorized File Upload [Must Have]
Description: The Administrator selects a Data Type from the dropdown, then chooses or drags a CSV file into the upload zone. On clicking Upload Data, the system parses the file, joins records to existing students by STN, and stores the rows associated with the selected Data Type.
Acceptance Criteria: After successful upload, the system displays a confirmation message indicating the number of records loaded. The new file appears at the top of the Upload History. If the file structure is invalid, the system displays a validation message and does not process the file.
DI-2 CSV Format Validation [Must Have]
Description: For each supported Data Type, the system validates the uploaded CSV against the expected structure before processing. Validation includes file type, required columns, expected identifiers, and required values needed for matching, display, tiering, and reporting.
Acceptance Criteria: If the uploaded CSV is missing required columns, has an unsupported structure, or does not align with the selected Data Type, the system displays a clear validation message and does not ingest the file. Valid files proceed to STN matching and record loading.
DI-3 Duplicate File Prevention [Must Have]
Description: If the Administrator attempts to upload an exact duplicate of a file that already exists in Upload History (matching file name and content hash), the system rejects the upload.
Acceptance Criteria: An error message is displayed: “This file has already been uploaded.” The upload does not proceed, and Upload History is unchanged.  
DI-3 File Type Independence [Must Have]
Description: The system identifies the Data Type from the dropdown selection at upload time, not from the file name. File naming conventions vary across districts and assessment vendors and must not affect categorization.
Acceptance Criteria: Two files with identical content but different names can both be uploaded only once each. Two files with different content but the same name can both be uploaded under different Data Types if categorized correctly.
To confirm: Should duplicate detection use both file name and content hash, or content hash only?
DI-4 Upload History Display [Must Have]
Description: Upload History displays a chronological list (most recent first) of every file uploaded, including Upload Date and Time (timestamped to the minute), File Name, Data Type, and Record Count.
Acceptance Criteria: All four data points are visible without scrolling on a 1280×720 viewport for the first ten entries. Older entries are paginated or scrollable.
DI-5 Delete Uploaded File [Must Have]
Description: Each row in Upload History exposes a Delete action. On confirmation, the file and all records sourced exclusively from it are removed. Records that were also represented in other files (e.g., a student already covered by a more recent demographic file) remain intact based on their newer source.
Acceptance Criteria: After deletion, the Upload History row is removed, and the Student Directory reflects the change. The audit trail records the deletion.
DI-6 Re-upload Under Correct Category [Must Have]
Description: If a file was uploaded under the wrong Data Type, the Administrator deletes it from Upload History and re-uploads it with the correct Data Type selection. Where expected file structure differs depending on Data Type, the system should flag files that do not match the selected Data Type before processing.
Acceptance Criteria: After re-upload, the file is categorized correctly, and student records reflect the new categorization.   If the uploaded file does not match the selected Data Type, the system displays a clear validation message and does not process the file.
Example: If an Admin selects ILEARN Checkpoint Data but uploads an IXL Diagnostic CSV, the system should identify that the file structure does not match the selected data type and display a clear validation message before processing.
Suggested validation message:
“The uploaded file does not match the selected data type. Please verify the file and select the correct Data Type before uploading.”
DI-7 Record Count Reporting [Must Have]
Description: Each successful upload displays the number of records (rows) ingested from the file.
Acceptance Criteria: The displayed record count matches the number of data rows (excluding header) in the source CSV.
DI-8 Per-File Size Limit  [Must Have]
Description: The system accepts CSV files up to 10 MB. Files exceeding the limit are rejected with a clear error message.
Acceptance Criteria: Uploading an 11 MB file produces an error: “File exceeds 10 MB limit.” No partial ingest occurs.
DI-9 Super Admin Reset (Optional) [Should Have]
Description: A reset-all-data utility is available only to users with the Super Admin role. It clears all uploaded files, ingested records, tier assignments, and audit history from the environment.
Acceptance Criteria: The reset action requires a confirmation dialog with typed confirmation (e.g., the word RESET). Reset is logged with actor, timestamp, and pre-reset record counts.
DI-10 STN Reconciliation Report [Must Have]
Description: When a non-demographic file (e.g., ILEARN, IXL) contains an STN that does not match any STN in the most recent demographics upload, the system flags the orphaned STN and exposes the list to the Administrator.
Acceptance Criteria: The Administrator can view a list of unmatched STNs after each upload and download it as a CSV.

8.2.2 Detailed Requirements
ST-1 Display All Loaded Students [Must Have]
Description: Once at least one student data file has been ingested, every student is listed in the Student Directory regardless of whether their tier has been processed.
Acceptance Criteria: After uploading a demographics file with N rows, the directory displays N rows (one per student).
ST-2 Search by STN [Must Have]
Description: Entering an STN in the Student Search field and clicking Search filters the directory to the matching student. Partial-match search is acceptable but exact match must be supported.
Acceptance Criteria: Searching for a known STN returns exactly one row. Searching for a non-existent STN displays a friendly empty state.
Should the Student Directory also support search by Student Name in addition to STN for MVP?

ST-3 Three-State Workflow Status [Must Have]
Description:
Each student displays one of three workflow states:
Pending — required data is missing or insufficient to compute a tier. 
System Recommended — the system has generated a recommended tier using approved LGS rules, but the Administrator has not finalized the decision. 
Finalized — the Administrator has confirmed or changed the tier and saved the final decision. 
Acceptance Criteria:
A student remains Pending until the minimum required data is available. Once sufficient data is available, the system generates a recommended tier and shows the student as System Recommended. When the Administrator saves the selected tier from the Override/Finalize Tier dropdown, the status changes to Finalized. Re-running the recommendation on a Finalized student does not remove or overwrite previous audit history.
ST-4 Pending State for Insufficient Data [Must Have]
Description: When a student record exists but cannot be tiered because of missing required data (e.g., no demographics OR no assessment matches), the system shows the student as Pending and the Generate AI Recommendation button is disabled with a tooltip explaining why.
Acceptance Criteria: A student in the directory whose STN has no demographic match shows Pending; opening their profile shows disabled Generate button and a message indicating the missing data category.
ST-5 Auto-Generate Recommendation on New Data Arrival [Must Have]
Description: As soon as a student has the minimum required data to compute a tier, the system automatically generates a System Recommended tier without administrator action. Only students with insufficient data remain in Pending.
Acceptance Criteria: After uploading sufficient assessment data for previously Pending students, those students appear with “System Recommended” status the next time the directory is loaded.
ST-6 Sort by Any Column [Must Have]
Description: The Administrator can click any sortable column header to sort ascending; clicking again toggles descending. The active sort indicator is visible.
Acceptance Criteria: Sorting by Tier descending puts Tier 3 at the top. Sorting by Grade ascending puts Grade 0 (Kindergarten) at the top.
ST-7 Pagination [Should Have]
Description: If the directory contains more rows than fit on one viewport, pagination or virtualized scrolling is provided to handle the full school population without performance degradation.
Acceptance Criteria: A directory containing 100 students loads its first page in under 2 seconds. Scrolling or paging through all students remains responsive.

ST-15 Generate AI Recommendation [Must Have]
Description: Clicking Generate AI Recommendation invokes the configured LLM (Meta Llama) with the student’s demographics and full assessment record. The system returns a Tier recommendation (1, 2, or 3) and a reasoning string referencing the latest assessments and proficiency levels. The AI-generated summary, where enabled, uses the students’ available assessment data to provide academic context for review.

The Collaboration Notes section receives an AI Summary entry that summarizes the student’s assessment history in clear language.
• The AI Summary supports Admin review and academic discussion but does not replace the approved tiering rules or the Administrator’s final decision.

ST-16 Tier Calculation Rules - Tooltip [Must Have]
Description: The application displays a tooltip near tier-related controls explaining the rule set used to compute the recommended tier. 
Acceptance Criteria: Hovering or focusing the info icon next to “Generate AI Recommendation” displays the tier rules. Editing the rules is a configuration task, not a UI task.
ST-17 Override / Finalize Tier [Must Have]
Description: The Administrator selects a Tier from the Override/Finalize Tier dropdown and clicks Save. The tier becomes Finalized; an Audit Trail entry “Tier Overridden / Finalized by Admin” records the action with timestamp and prior-vs-new tier values.
Acceptance Criteria: Saving Tier 1 for a student previously System Recommended at Tier 3 produces an audit entry capturing both values. The Tier Indicator updates to Tier 1 (Finalized).
ST-18 Re-Finalization [Must Have]
Description: An Administrator can change a Finalized tier at any time. Each change generates a new Audit Trail entry; previous entries are never modified or deleted.
Acceptance Criteria: Changing a Finalized Tier 1 to Tier 2 produces a second audit entry without overwriting the first.
ST-19 AI Collaboration Summary [Must Have]
Description: When the recommendation workflow is generated, a narrative AI Summary is added to Collaboration Notes. The summary should consider all available assessment records for the student and summarize the academic story by subject and assessment type, including recent performance, strengths, concerns, and trends were supported by the data.
Acceptance Criteria: An AI Summary appears within 30 seconds of clicking the recommendation action. The summary references the student’s available assessment history, uses proficiency/performance levels as the primary interpretation, includes scores only as supporting context, and avoids unsupported comparisons across different assessment types or scoring scales.
Note: Refer to Appendix B.3 – Sample AI Summary Output for the expected structure, tone, and level of detail.
ST-20 Free-Text Collaboration Notes [Must Have]
Description: Administrators can post free-text notes via the Add a note input. Each note is timestamped and attributable to the user.
Acceptance Criteria: After clicking Post, the note appears in Collaboration Notes with date and (once auth is in place) author. Notes cannot be edited after posting; only deleted, with deletion captured in the audit trail.
ST-21 Immutable Audit Trail [Must Have]
Description: All tier changes (system-generated and administrator-driven) and key actions are written to the Audit Trail. Audit entries are append-only and cannot be modified.
Acceptance Criteria: Direct database edits are out of scope; the application does not expose any UI for editing or removing audit entries.

10. Tier Recommendation Engine & AI Summarization
10.1 Tier Recommendation Logic
The tier recommendation logic is the core decisioning engine of LGS Pathways Studio. The April 9 meeting confirmed that the prototype encodes a draft ruleset gathered from prior development (Sandip’s code) and that the authoritative ruleset must be confirmed by LGS before the production engine is finalized. The current code reveals the following operational ruleset, which must be reviewed and approved (or amended) by LGS:
Step 1 - Identify the most recent assessment for each subject
The engine sorts all assessments for the student by date (descending) and selects the most recent ELA assessment and the most recent Math assessment from the result. Subject is normalized to either “ELA” or “Math” using filename heuristics (e.g., a filename containing “Math” or “Mathematics” maps to Math; “ELA” or “English” maps to ELA) and the IXL-specific suffix logic (IXL-ELA / IXL-Math).
Step 2 - Determine “On/Above” for each subject
For each of the two subjects, the engine first inspects the proficiency string (Performance Level, Proficiency Level, Status, or Achievement Level field) using the following case-insensitive rules:
Strings containing “below”, “far below”, or “approaching” evaluate to FALSE (not on/above).
Strings containing “above”, “on grade”, “at grade”, “at proficiency”, “proficient”, “meets”, or “exceeds” evaluate to TRUE (on/above).
A literal string of “Tier 1” evaluates to TRUE; “Tier 2” or “Tier 3” evaluates to FALSE.
Strings of “mid above” or “early on” evaluate to TRUE.
If the proficiency string is missing or unrecognized, the engine falls back to the percentile field (any source field whose name contains “percentile”). A percentile value of 40 or greater evaluates to TRUE; a value below 40 evaluates to FALSE. The 40th-percentile threshold is the operative cutoff for “on grade level” in the current implementation and is a key value that LGS must confirm or amend.
Step 3 - Combine ELA and Math signals to produce a tier
With ELA and Math each evaluated to TRUE (on/above) or FALSE (below):
ELA TRUE AND Math TRUE → Tier 1
ELA FALSE AND Math FALSE → Tier 3
Mixed (one TRUE, one FALSE) → Tier 2
If only one subject can be evaluated (e.g., a Kindergarten student with only reading data), the engine uses that subject’s value for both ELA and Math, effectively producing Tier 1 if on/above, Tier 3 if below. This single-subject behavior must be reviewed with LGS, especially in the context of K–2 students who do not yet have ILEARN data.
Each recommendation is accompanied by a reasoning string in the format: “Based on ELA ([proficiency] -> On/Above|Below) and Math ([proficiency] -> On/Above|Below).”
10.2 AI Summarization Logic
The AI Summary is generated alongside the tier recommendation. It is a paragraph-form narrative describing the student’s academic story across the available assessments. It is explicitly not a predictive model. The production implementation will use a Meta Llama-family large language model accessed via the .NET 8 backend; the specific Llama variant and Azure hosting target is to be confirmed during the Azure Infrastructure work in Section 17.1. The reference prototype used Google Gemini gemini-2.5-flash, but no Gemini code or credentials will ship to production.
Per Velvet Wright’s feedback, the prompt must be tuned so the summary minimizes unexplained numeric figures and produces sentences that are meaningful to a non-technical reader (e.g., a teacher in a data-talk meeting).
10.2.1 Prompt Composition
The prompt sent to Meta Llama is composed server-side by the .NET 8 API (never assembled in the browser). It contains the following components, in order, and is externally configurable per requirement AI-4:
Instruction to produce a concise, chronological summary of the student’s academic progress.
Instruction to highlight trends, strengths, and areas of concern.
Instruction to compare the student’s performance to LGS (Local Grade/School) averages.
Instruction to avoid markdown headers and produce clean prose.
The student’s grade level (passed as a tokenized identifier, never the student’s name or STN — see Section 11.1.5 PII Redaction).
The pre-computed LGS averages for ELA and Math, sourced from a server-side aggregation cached in Cosmos DB (not recomputed on every call).
A list of the student’s assessments (date, type, subject, score, proficiency band) sorted chronologically.
Before any prompt leaves the .NET API, it passes through the Pii Redaction Service which removes student name, STN, date of birth, address, and any free-text demographic identifiers. The Llama endpoint receives only assessment data and a non-identifying token. Output is reviewed by an output filter that removes any identifier that may have been hallucinated or echoed by the model.

11. Non-Functional Requirements
11.1 Security & PII Compliance
Student demographic and assessment data are protected by FERPA and by LGS information-security policy. The Azure target architecture must implement defense-in-depth across authentication, transport, storage, application, and observability layers. 
11.1.1 Authentication
NF-SEC-1 Authentication (Basic for MVP) [Must Have]
Description: All access requires authenticated login via ASP.NET Identity (or JWT-based equivalent). Credentials are hashed with the ASP.NET Identity password hasher (PBKDF2 with HMAC-SHA256, 10,000+ iterations). SSO is deferred (Task 15: Basic auth for MVP - no SSO).
Acceptance Criteria: No anonymous endpoint exists in the API except /health and /api/auth/login. Stored passwords pass an inspection that confirms PBKDF2 format. JWT bearer tokens are signed with a key sourced from Azure Key Vault and rotate on key revocation.
11.1.2 Role-Based Access Control
NF-SEC-2 Role-Based Access Control [Must Have]
Description: The .NET 8 API enforces RBAC via authorization policies. MVP roles are Administrator and Super Admin.
Acceptance Criteria: An Administrator-bearing token cannot call any Super Admin endpoint. Endpoint authorization is unit-tested against representative role/endpoint combinations.
11.1.3 Encryption in Transit and at Rest
NF-SEC-3 Encryption - In Transit and at Rest [Must Have]
Description: All HTTP traffic is HTTPS-only with TLS 1.2 minimum HSTS headers are emitted by the App Service. Cosmos DB encrypts at rest by default (service-managed keys). Azure Blob Storage encrypts at rest. Azure Key Vault holds all secrets.
Acceptance Criteria: An external HTTPS scanner (e.g., SSL Labs) returns A or higher. Cosmos and Blob portal blades show encryption-at-rest enabled. App Service shows HTTPS-only and TLS 1.2 minimum enforced.
11.1.4 PII Field Inventory
PII-1 PII Field Inventory & Data Classification [Must Have]
Description: All PII fields handled by the application are inventoried into three sensitivity tiers and a data flow map is maintained Tier 1: directly identifying (name, DOB, address, STN). Tier 2: quasi-identifying when combined (ethnicity, school entry/exit dates, lunch status, EL/SPED/504 indicators, homeroom). Tier 3: assessment scores and proficiency bands.
Acceptance Criteria: A signed-off PII inventory document exists, classifying at least 12 fields. The data flow map shows source → ingestion → storage → API response → AI prompt for each Tier 1 and Tier 2 field, with the redaction or masking control applied at each step.
11.1.5 PII Redaction Before Llama Calls
PII-2 PII Redaction in LLM Prompts [Must Have]
Description: A .NET Pii Redaction Service strips all Tier 1 PII from the prompt before it is sent to the Llama endpoint. The student is referenced only by a non-reversible token (e.g., a per-request opaque ID derived from the STN with a Key-Vault-held salt). Names, STN, DOB, and addresses never reach the LLM. The output is re-scanned for any leaked identifier; if found, the response is rejected and the user sees a generic error.
Acceptance Criteria: Inspection of recorded LLM prompts (in the App Insights LLM dependency channel after PII scrubbing) confirms no Tier 1 field is present. Penetration testing tries to bait the LLM into echoing names — output filter catches and blocks.
11.1.6 Application Insights PII Scrubber
PII-3 Telemetry PII Scrubber [Must Have]
Description: An Application Insights Telemetry Initializer in the .NET 8 API strips any PII from request/response logs, exception messages, and Llama dependency telemetry before it is shipped to App Insights.
Acceptance Criteria: Sample queries against the App Insights workspace for last-7-days requests, exceptions, and dependencies return zero hits when searching for any sample student name, STN, or DOB used in test data.
11.1.7 Audit Logging Middleware
PII-4 Audit Logging Middleware [Must Have]
Description: An ASP.NET Core middleware records every request that touches a PII-bearing endpoint into the audit logs container. The recorded payload contains the user UID, action, timestamp, client IP, and correlation ID. Request bodies are never logged in full; only the action descriptor.
Acceptance Criteria: Every read of /api/students/{stn} and /api/students/{stn}/* by a non-system actor produces an audit_logs entry. Entries are visible to admins via /api/audit and survive a 30-day Cosmos retention check.
11.1.8 Equivalent of Dynamic Data Masking
PII-5 Cosmos DB Output Masking  [Must Have]
Description: Cosmos DB does not natively offer Dynamic Data Masking the way Azure SQL does. For Cosmos, the equivalent is enforced at the .NET API output projection: any Tier 1 PII field is masked unless the requesting user is an Administrator. The mask is applied in the response DTO; the raw value never leaves the API process for non-admin requests.
Acceptance Criteria: An automated test asserts that a teacher-role token receives masked values for name, DOB, and address fields, while an admin-role token receives the unmasked values. Cosmos itself never returns the unmasked field via direct SDK access for non-admin contexts because all access is mediated by the API.
11.1.9 Export Watermarking
PII-6 Watermarked Export [Must Have]
Description: Every export produced via ClosedXML carries a header and footer with the requesting user’s name, the export timestamp, and a confidentiality notice. The export is also logged to audit logs.
Acceptance Criteria: Generated files open in Excel with the watermark visible in print preview and on the first row. The audit log shows one entry per export.
11.1.10 Secrets Management
PII-7 Secrets in Azure Key Vault Only [Must Have]
Description: All secrets, Cosmos DB connection string, Llama endpoint and key, JWT signing key, third-party API keys are stored in Azure Key Vault and accessed by the App Service via Managed Identity. Secrets never appear in app settings, environment files, or source control.
Acceptance Criteria: A repository scan (e.g., gitleaks, GitHub secret scanning) returns no matches. App Service configuration shows Key Vault references rather than literal values. Managed Identity has the “Key Vault Secrets User” role and no broader access.
11.1.11 Closed-List User Provisioning
PII-8 Closed-List Provisioning [Must Have]
Description: User accounts are created only by an existing Administrator (or by a documented one-time bootstrap process for the first admin). Self-signup is disabled in production.
Acceptance Criteria: Attempting to create a new user via the public sign-up surface returns 403. Only authenticated admin endpoints can create users.
11.2 Performance
NF-PERF-1 Page Load [Should Have]
Description: Each primary screen (Dashboard, Students, Data Ingestion, Student Profile) loads within 3 seconds on a modern broadband connection for a school of up to 1,000 students.
Acceptance Criteria: Lighthouse / synthetic test of each route returns Largest Contentful Paint ≤ 3.0 s.
NF-PERF-2 Ingestion Throughput [Should Have]
Description: A 10 MB CSV upload (~50,000 rows) completes ingestion within 60 seconds.
Acceptance Criteria: Sample upload meets target on production-equivalent infrastructure.
NF-PERF-3 LGS-Average Aggregation Scalability [Must Have]
Description: The LGS-wide average ELA and Math scores used in the AI prompt must be computed by a server-side aggregation in the .NET 8 API and cached in Cosmos DB (e.g., a metrics container with a small set of documents holding rolling averages). Aggregation must NOT read the entire assessments container on every Generate AI Recommendation request.
Acceptance Criteria: On a database of 5,000+ assessment records, generating a tier recommendation completes in under 30 seconds. The metric is updated either on a schedule (e.g., nightly Azure Function) or on-write via a change-feed processor; the read path is O(1).
NF-PERF-4 Bulk Ingestion Write Pattern [Must Have]
Description: CSV ingestion in the .NET 8 API must use Cosmos DB bulk-write transactions (TransactionalBatch, Bulk Executor, or the v3 SDK AllowBulkExecution mode) when persisting demographic or assessment rows. 
Acceptance Criteria: Ingesting a 10,000-row CSV completes in under 60 seconds and is observable in Application Insights as bulk operations rather than individual writes.
11.3 Reliability & Availability
